# Part 3 JSON API contract

Frozen frontend contract, version 1. All routes have `/api/trade` prefix. JSON uses snake_case. All weights are positive integer **grams**; money is integer **paise**, unit prices paise/kg; currency INR. ISO timestamps are UTC. Generated IDs are opaque strings. Resource responses include `id`, `version` (integer), `created_at`, `updated_at`, plus the fields below. A command returns the changed resource, except session creation. Errors return `{ "detail": "human readable reason" }` with 401/403/404/409/422/503. Every authenticated POST requires a unique `Idempotency-Key` header; retries of an identical path/body replay the original result; changed intent conflicts. Transition commands require `expected_version` equal to current resource version. GET never needs an idempotency key.

## Sessions and workspace

- `GET /health`: `{status, mode, synthetic, production_ready, blockers, server_time}`.
- `GET /dev/principals`: `{principals: [{id, display_name, organisation_id, role}], synthetic: true}`; available only with explicit `TRADE_DEMO_MODE=1` and `TRADE_ENV=development`. Staging and production fail closed.
- `POST /dev/sessions` body `{principal_id}` returns `{token, principal: {id, display_name, organisation_id, role}, synthetic: true}`. Keep token in memory/session storage. All remaining requests use `Authorization: Bearer <token>`; organisation headers are ignored. IDs: `fpo-a`, `fpo-b`, `exporter-a`, `exporter-b`, `qc-a`, `qc-b`, `finance-a`, `finance-b`. Roles: `fpo`, `exporter`, `qc_reviewer`, `finance_reviewer`. Reviewer A belongs to FPO A; reviewer B to FPO B. These identities and all capacity fixtures are synthetic.
- `GET /workspace` returns `{server_time, synthetic, principal, production_ready, blockers, requirements: [], proposals: [], lots: [], capacities: [], auctions: [], contracts: [], shipments: [], receipts: [], claims: [], settlements: [], audit_events: []}`. Arrays contain scoped resources only; auctions contain public market fields and only bids visible to the caller. Refresh after commands. Development capacity fixtures are `capacity-a` and `capacity-b` (1,000,000g each, crop okra, variety okra, grade A, grade_protocol export-v1, broad future window), scoped to the corresponding FPO. Buyer lot views omit member contributions; buyer settlement views omit private member allocations/disbursals/payment evidence.
- `GET /{collection}/{id}` and `GET /{collection}` for `lots`, `capacities`, `auctions`, `contracts`, `shipments`, `receipts`, `claims`, `settlements`; list response `{items: [...]}`. Auction public views omit other organisations' private offers/evidence. IDs belonging to inaccessible resources return 404.

## Lots and QC

- `POST /lots` (FPO): `{crop, variety, grade, quantity_g, harvest_date, pickup_deadline, member_contributions: [{member_id, quantity_g}]}`. Contributions must sum to quantity. Dates are ISO dates/timestamps; `harvest_date` is YYYY-MM-DD. Result adds `seller_org`, `status: "held"`, `qc_status: "pending"`, `reserved_g: 0`, `shipped_g: 0`, `inspections: []`, `reviews: []`, `forward_contract_id: null`.
- `POST /lots/{id}/inspections` (own FPO): `{expected_version, sample_id, protocol, protocol_version, inspected_weight_g, sample_count, observed_grade, defects, report_reference, issuer, inspected_at, safety_hold}`. Strings nonempty, inspected_at ISO timestamp. Adds immutable inspection and resets release to pending/held.
- `POST /lots/{id}/reviews` (assigned QC): `{expected_version, decision: "release"|"hold", reason}`. Release requires at least one safe inspection of the declared grade. Its `inspected_at` must be **strictly later than every prior safety-hold observation**; older or equal-time safe evidence cannot clear a newer hold regardless of append order. Explicit release records `superseded_safety_hold_ids` on the immutable review. Adds review; sets `qc_status` and status. Private report references never appear on public opportunity views.

## Buyer requirements and FPO proposals

- `GET /requirements` and `GET /requirements/{id}` return requirements owned by the exporter or published requirements visible to FPOs. Drafts are private to their owner. Workspace also returns scoped `requirements` and `proposals` arrays.
- `POST /requirements` (exporter): creates a draft with `{crop, variety, grade, quantity_g, maximum_price_paise_per_kg, proposal_deadline, handover, grade_protocol, payment_terms, delivery_start, delivery_end, payment_due_days, downgrade_bps, fee_paise, shortfall_liability, cancellation_terms, production_risk, dispute_procedure, quality_specification?, packaging_requirements?, additional_requirements?}`. The proposal deadline must be in the future and no later than delivery end; it may precede delivery start. Quality criteria are buyer-defined objects `{attribute, unit?, minimum?, maximum?, required?, notes?}`; no universal thresholds are assumed.
- `POST /requirements/{id}/publish`: `{expected_version}`. Opens the requirement until its server deadline. The worker expires the requirement and releases all still-active proposal reservations after that deadline.
- `POST /requirements/{id}/proposals` (FPO): `{quantity_g, grade, price_paise_per_kg, expected_availability, capacity_id, evidence_reference?, notes?}`. Partial or full quantities are accepted, up to the requirement's current `remaining_g`; capacity must be consented, reviewed, compatible and available across the delivery window. Each proposal reserves its offered quantity. A second active proposal from the same FPO is rejected. Withdraw and resubmit to change an offer.
- `POST /proposals/{id}/withdraw` (own FPO) and `/reject` (requirement owner exporter): `{expected_version}`; reject also requires a recorded `reason`. Both release reserved capacity. Buyer proposal views omit supplier capacity and reservation identifiers; private evidence references are not a substitute for authorised document storage.
- `POST /requirements/{id}/award` (owner exporter): `{expected_version, proposal_id}`. The exporter explicitly selects each proposal; no automatic ranking or runner-up award. Each selected proposal creates one provisional forward contract with `requirement_id` and `proposal_id` links, then uses bilateral confirmation. An already-awarded proposal cannot be awarded again. Multiple FPO contracts may cover one requirement (for example, 60kg and 40kg against 100kg). The trade transaction lock and version check prevent competing awards exceeding the quantity budget; a proposal larger than the remaining quantity must be withdrawn and resubmitted smaller.
- Requirement allocation fields: `allocated_g` is the sum of non-expired/non-cancelled/non-defaulted award contracts, including provisional awards; `remaining_g = quantity_g - allocated_g`. `allocation_status` is `unallocated`, `partially_awarded` or `fully_awarded`. A partial requirement stays `published` until its deadline; a fully allocated requirement becomes `awarded`. `contract_ids` and `awarded_proposal_ids` retain all linked award history, including ended contracts; legacy singular `contract_id` and `awarded_proposal_id` identify the most recent award. Read access to each contract remains party-scoped.
- Unselected submitted proposals retain reservations while quantity remains open. Only a full allocation marks those proposals `not_selected` and releases them; deadline expiry marks them `expired` and releases them. Winning reservations belong to their contracts and are not released a second time when the requirement expires. Contract cancellation/default/expiry restores its allocated quantity; the requirement reopens only before its original deadline, without selecting another FPO automatically.

## Auctions and offers

- `POST /auctions` spot (FPO): `{mode: "spot", lot_id, reserve_price_paise_per_kg, increment_paise_per_kg, opens_at, closes_at, handover, grade_protocol, payment_terms, delivery_start, delivery_end, payment_due_days, downgrade_bps, fee_paise, shortfall_liability, cancellation_terms, production_risk, dispute_procedure}`.
- `POST /auctions` forward (exporter): same commercial fields, `{mode: "forward", crop, variety, grade, quantity_g, maximum_price_paise_per_kg, opens_at, closes_at, ...}`; no lot, reserve or increment. Default opens_at now and closes_at +2h if omitted. Explicit close must follow open. `downgrade_bps` is 0..10000 fraction of full price. `fee_paise` charged to seller is disclosed. `shortfall_liability` is `seller` or `buyer`.
- Auction result fields: `mode`, `owner_org`, `seller_org` (spot), crop/variety/grade, quantity_g, `status: "scheduled"|"open"|"awarded"|"no_sale"|"cancelled"`, `opens_at`, `original_closes_at`, `closes_at`, `extension_seconds` (spot cap 600), `extension_window_seconds:120`, pricing/commercial fields, `bids: [{id, organisation_id, price_paise_per_kg, accepted_at, sequence, capacity_id?, status}]`, `leading_price_paise_per_kg`, `contract_id` nullable. Status open is projected from server clock; close is persisted by worker.
- `POST /auctions/{id}/bids` (exporter spot / FPO forward): `{expected_version, price_paise_per_kg, capacity_id?}`. Spot must meet reserve and improve leader by increment. Forward must not exceed maximum, is whole-request only, and requires compatible consented/reviewed capacity with sufficient available_g. A supplier may replace its own offer at a strictly lower price; all revisions retained. Earliest acceptance sequence breaks forward ties. Spot late bid extends close to now+120s capped at original+600s. Bid response is the updated auction including caller-visible receipt.
- `POST /auctions/{id}/cancel`: `{expected_version, reason}` owner only, before award; releases reserved stock/capacity.
- `POST /auctions/{id}/close`: `{expected_version}` owner only; rejects before effective close. This is an operator recovery endpoint; server worker owns unattended closing. Closing is idempotent and creates at most one provisional contract.

## Contracts and harvest conversion

- Contract fields: `auction_id`, `seller_org`, `buyer_org`, `mode`, `lot_id` nullable, `capacity_id` nullable, `quantity_g`, `price_paise_per_kg`, `status: "provisional"|"confirmed"|"expired"|"cancelled"|"defaulted"`, `terms_version`, `terms` (commercial snapshot above), `confirmations: [{organisation_id, terms_version, confirmed_at}]`, `expires_at`, `shipped_g`.
- `POST /contracts/{id}/confirm`: `{expected_version, terms_version}` either party. Both organisations must confirm same terms version; then status confirmed. Provisional deadline is award close +24h. Worker expires and releases unconfirmed awards.
- `POST /contracts/{id}/amend`: `{expected_version, terms}` either party, before any shipment. `terms` is a complete replacement commercial snapshot; quantity, price, seller and buyer cannot change. Creates a new version, clears confirmations, returns provisional with new 24h expiry. Changing terms requires renewed bilateral approval.
- `POST /contracts/{id}/cancel` or `/default`: `{expected_version, reason}` either party before any shipment; records actor and reason, releases reservation. No runner-up award.
- `POST /contracts/{id}/harvest`: seller of confirmed forward only. `{expected_version, quantity_g, harvest_date, pickup_deadline, member_contributions}`. Creates held lot for entire quantity only, with crop/variety/grade from contract and `forward_contract_id`. Atomically converts committed capacity into exclusive lot reservation; does not expose it to spot auctions. Response is created lot; refresh workspace to obtain changed contract.

## Shipments and receiving

- `POST /shipments` seller only: `{contract_id, lot_id, quantity_g, pickup_at, delivery_at, packing, handover_reference}`. Confirmed contract, released QC and remaining stock/contract quantity required. Result `status: "draft"`, `seller_org`, `buyer_org`; draft immediately reserves cumulative shipment quantity against both lot and contract.
- `POST /shipments/{id}/dispatch`: `{expected_version}` seller only, rechecks QC release; records immutable dispatch time.
- `POST /shipments/{id}/receive`: buyer only `{expected_version, received_g, accepted_g, downgraded_g, rejected_g, reason, evidence_reference}`. Sum accepted+downgraded+rejected equals received; received <= shipped; missing weight is transit_shortfall_g. Downgrade/rejection/shortfall require reason. Creates receipt, marks shipment received. Response is receipt (refresh workspace).
- Receipt fields: shipment_id/contract_id/seller_org/buyer_org, quantity_g, received_g, accepted_g, downgraded_g, rejected_g, transit_shortfall_g, reason, evidence_reference, received_at.

## Claims and settlements

- `POST /claims` either receipt party: `{receipt_id, affected_g, amount_paise, direction?, reason, evidence_reference}`. Direction is immutable `seller_deduction` (default, backward compatible) or `seller_credit`. Positive affected weight and amount; cumulative affected weight cannot exceed shipment. Deduction requests cannot exceed attributable recognised receipt gross. Credit requests dispute an unpaid rejection, seller-liable transit shortfall or downgrade: the server records disjoint `credit_attribution` segments with quantity, maximum credit and `requested_credit_paise`. Fully accepted/already recognised weight cannot receive credit; downgraded weight is capped at its rounded full-price amount minus its rounded already recognised amount. Component-level cumulative credit budgets prevent separate requests creating additional rounding recovery. Total requested credits cannot exceed the original full-price **receipt component-line** obligation minus recognised receipt gross. All-rejected receipts can therefore open credit claims while retaining their original receiving facts. Open claim holds settlement; request alone changes no obligation.
- `POST /claims/{id}/propose`: `{expected_version, adjustment_paise, reason}` either party. Adjustment is a nonnegative magnitude, <= requested amount, applied according to the claim's immutable direction. A changed direction is rejected. Creates resolution version, clears prior approvals.
- `POST /claims/{id}/agree`: `{expected_version, resolution_version}` either party; both parties approve the exact resolution. Then claim `status: "resolved"`; settlement uses only agreed amount. Claim fields include requested amount_paise, status, proposal `{version, adjustment_paise, reason}`, approvals.
- `POST /settlements` seller only: `{contract_id}`. Requires all contract quantity received and no open claims. Final integer ledger result: `gross_paise` (accepted*price + downgraded*agreed rate; buyer-liable shortfall at full rate), `deductions_paise`, `credits_paise`, signed `adjustments_paise = deductions_paise - credits_paise`, `fee_paise`, `net_paise`, `allocations: [{member_id, contribution_g, amount_paise}]`, `invoice_paise = gross_paise - deductions_paise + credits_paise`, `original_obligation_paise`, `payment_status: "unverified"`, `verified_receipt_paise: 0`, `disbursed_paise: 0`. Only bilaterally resolved adjustments apply. Reject invoices above the original full-price receipt component-line obligation, negative net and totals outside JSON's safe integer range. Largest remainder allocation breaks ties by member_id; allocations sum exactly to net. Multiple lots' contribution weights summed by member. One immutable settlement per contract. `payment_due_at` is anchored to the latest actual receipt plus agreed payment_due_days, independent of statement issuance time.

**Money line rounding:** for each receipt, accepted, downgraded, rejected and transit-shortfall quantities are separate lines. Each line's `grams × paise_per_kg × rate_bps / 10,000,000` rounds half-up to paise; recognised gross sums the payable lines at their agreed rates. The recovery ceiling `original_obligation_paise` sums those same lines at the full contract rate across all receipts. It does **not** re-round the aggregated contract weight. For example, two accepted 1g receipts at 500 paise/kg each round to 1 paise and settle at 2 paise; an accepted 1g line plus a full-rate downgraded 1g line in one receipt use the same 2-paise ceiling. Receipt partitions must equal their receipt quantity, and receipt quantities must equal contracted quantity. Credits retain both the affected-weight cap and each unpaid component's rounded full-price-minus-recognised budget; repeated claims cannot add rounding recovery.
- `POST /settlements/{id}/payments` finance reviewer of seller: `{expected_version, amount_paise, evidence_reference, verification_basis}`. Cumulative verified receipt <= invoice; records verifier and time; status `part_paid` or `paid`. Does not move money.
- `POST /settlements/{id}/disbursals` finance reviewer of seller: `{expected_version, member_id, amount_paise, evidence_reference, verification_basis}`. Cumulative per member <= allocation and total <= verified FPO receipts minus fee; records verifier and time. Separate member reconciliation, no fund movement.

## Operation and gates

Required custom `quality_specification` criteria are preserved commercial obligations, not assessed measurements. Until a criterion-specific review adapter binds evidence to the current terms and inspection, shipment creation and dispatch reject contracts with any required custom criterion. Optional preferences remain visible but do not assert compliance. Do not remove or downgrade a requirement merely to bypass review; legitimate changes use versioned bilateral amendment and confirmation.

App `server.app:app`, worker `python -m server.worker` (repeat interval configurable; `--once` for one durable recovery pass). `TRADE_DATABASE_URL=sqlite:///./server/trade-dev.sqlite3` by default. `TRADE_DEMO_MODE=1` explicitly enables synthetic sessions/capacity. `TRADE_ENV=production` rejects demo and all trade commands until real Part 2 identity/capacity adapters are installed. PostgreSQL target URL `postgresql+psycopg://...`. Every command's state change, audit event and idempotency response commit in one database transaction. PostgreSQL row locking serialises trade writes; SQLite uses BEGIN IMMEDIATE solely for local development/tests. No browser is needed to close or expire awards.
