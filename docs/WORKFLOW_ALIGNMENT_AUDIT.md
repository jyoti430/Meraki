# Frontend/backend workflow alignment audit

Reviewed 16 November 2026 on Kireeti, starting at `bc1b051`. The user-supplied **Exporter-Sponsored Procurement Workflow Addendum** dated 16 November was reviewed as the intended alignment target. It explicitly describes a proposal, not evidence of implemented features. This audit does not imply that partnerships, private procurement or subscriptions already exist. Fresh fetch found no pending remote branch outside the starting checkout.

## Main finding

Meraki has useful domain modules, but not yet one connected procurement workflow. There are three independent state authorities:

| Authority | Actual owner and persistence | What its green status means |
|---|---|---|
| Local FPO/planning/lot/lab and exporter demo | React contexts, services and browser storage | A local scenario/draft/review was changed; not a shared booking, verified login or signed obligation |
| Shared Part 2 `/api/v1` | `server/meraki/`, its database and permission checks | A scoped projection/capacity/listing/reservation operation was stored in the shared service |
| Part 3 `/api/trade` | `server/app.py`, `server/service.py`, separate ledger/session model | A development trade command was server-validated in that ledger; its capacities and actors are synthetic adapters |

Merging these files does not synchronize the databases, identities, quantities or decisions. The exporter UI does not call the shared procurement API. The current shared reservation path requires a public-to-members listing; there is no private partner allocation channel. A subscription must never be used as a shortcut around permissions, farmer participation or commercial agreement.

## Key contradictions and prevention

“Fixed” below concerns the stated narrow defect, not end-to-end procurement completion.

| Difference / failure example | Source evidence | Prevention and current disposition |
|---|---|---|
| Exporter A saves a requirement but FPO B cannot see that same record | `src/exporter/exporterService.ts` uses fixtures and local drafts; `server/meraki/models.py` has no requirement model | **Open P0:** shared exporter requirement API/history/commitment states, approved-recipient scopes and one requirement ID. Never silently convert a local draft into confirmed demand. |
| Generic org membership is mistaken for an approved exporter–FPO partnership | `server/meraki/app.py::actor`, `models.py::Membership`; no relationship/sponsorship entities | **Open P0:** many-to-many relationship with invited/active/suspended/revoked states and sharing scopes; check membership AND relationship AND action scope. Sponsorship is entitlement, not ownership/exclusivity. |
| Each exporter receives an independently editable copy of the same supply | Frontend synthetic projections versus shared `Projection.source_id/version` | **Open P0:** one FPO-owned, plot/cycle/week-linked source; exporter dashboards are permission-filtered views. Current versioning is a foundation, not authoritative physical-source identity across all modules. |
| Private procurement is forced through market publication | `server/meraki/services.py::reserve_capacity` requires an active member-visible `Listing` | **Open P0:** add a private request/approve/counteroffer allocation command under active partnership scopes. It must use the same source budget; do not simulate private procurement with a hidden/public listing workaround. |
| One 100 kg forecast becomes two 100 kg capacity records | `app.py::create_capacity` previously checked each row alone | **Fixed for a declared source/version:** lock the projection, bound aggregate capacity slices, retain withheld slices in the budget and include old-version commitments. New regression fails before the fix. PostgreSQL source-creation race test added. Different invented source IDs can still represent the same physical production until the canonical lineage contract is implemented. |
| A revised 100 kg forecast ignores 60 kg already committed on an older version | `publish_projection` preserves committed reservations for review; earlier `create_capacity` could repromise the entire revision | **Fixed budget guard:** older-version committed grams consume the new source budget; a test permits only 40 kg new capacity. Do not silently cancel obligations. A complete committed-contract amendment/default/release protocol remains open. |
| An okra grade-A week is republished as tomato, another grade or another week | `CapacityCreate` carried independent product/week fields | **Fixed:** exact crop/variety/grade/week agreement with the owned projection, rechecked by source eligibility. Legitimate transformations need a reviewed explicit contract, not relabelling. |
| Discovery hides stale supply but an existing reservation can still be confirmed | Shared reserve/list/confirm code previously applied different subsets of rules | **Fixed:** common source eligibility at discovery, capacity review, listing, reservation and confirmation; test stales the source after reservation and verifies confirmation fails. Existing committed obligations remain for review. Broader cross-operation/concurrent revocation acceptance still needs integration tests. |
| A string claiming “QC released” makes harvested stock tradable | Shared `review_capacity` previously accepted any nonempty evidence reference; local QC and Part 3 use different lot IDs | **Fixed fail-closed boundary:** shared harvested-lot approval/discovery/reservation now refuse without a verified Part 3 QC adapter. A text reference is not proof. Real lot/report/protocol/hold linkage remains open; existing Part 3 QC is retained rather than rebuilt. |
| A local QC release appears to release server stock | `LotsContext`, `LabReviewContext`, local `LabReviewService` versus `server/service.py` | **Mitigated, integration open:** local action pages state their authority; “Trade API” links now lead to `/trade/lots` and `/trade/review`. Local routes remain demos. Shared QC IDs and authenticated review import are still required. |
| Forecast, plan confirmation, farmer agreement, reservation and contract are all read as “confirmed” | `PlanContext`, `SupplyPlanningService::confirmSupplyPlan`, `server/meraki/services.py`, `server/service.py::contract_action` | **Mitigated, state mapping open:** local authority banner and proposal wording; backend confirmation still owns obligations. Define explicit proposed/accepted/planted/projected/reserved/provisional/bilateral-confirmed/harvested/paid states and allowed transitions. Do not map strings by name alone or treat HTTP 200 as proof of commitment: the shared expired-confirm path returns an `expired` reservation record, which a future adapter must inspect. |
| “Proceed/Sow” instructions precede farmer/buyer acceptance | `Overview.tsx`, `planning/messages.ts` | **Mitigated:** review-proposal wording replaces immediate planting imperatives; existing consent and reply states remain. No real messages are sent. Other legacy task/feasibility/aggregate labels still need a comprehensive approved-instruction readiness contract before field use. |
| A cached trade form remains actionable after the API fails | `TradeProvider.tsx`, `CommandForm` in `trade/ui.tsx` | **Fixed UX guard:** actions require a successful, authenticated snapshot received within 60 seconds; refresh/error states pause writes and the command function rechecks. Backend remains authoritative. Isolated browser outage test verified disabled fields/submit and retained read-only snapshot. |
| An old actor's draft or async result appears under a switched organisation | `TradeProvider::connect/command`, `TradeFrame` form subtree | **Fixed guard:** actor-keyed form remounts and session-generation checks before/after refresh. This is not a unified identity-provider implementation; the two backend token/permission schemes remain separate. |
| Wrong API response is cast to a valid trade workspace | `apiRequest<T>` previously provided only compile-time typing | **Fixed boundary:** runtime workspace envelope checks reject wrong-service/malformed responses and pause commands. Full shared OpenAPI/client schema generation is still recommended; envelope checks are not exhaustive per-resource validation. |
| One retry key on a different resource returns a previous operation's response | Shared `commit_idempotent` previously hashed body without route/resource | **Fixed:** include the operation path in the fingerprint. Same key plus different resource is a 409, not a misleading success. Old pre-fix stored keys fail closed on fingerprint mismatch; do not replace their key automatically after an uncertain outcome. |
| kg, g, hectares, acres, INR/paise and arbitrary buyer currency are mixed | `farmdata/projections.ts`, `types/index.ts::BuyerOrder`, `trade/calculations.ts`, shared `schemas.py` | **Partial:** Part 3 already uses exact decimal conversion/integer money. Shared gram inputs now reject booleans, strings, overflow beyond its PostgreSQL INTEGER range, and low/base/high inconsistencies. Adapters must convert explicitly, reject unsupported currency and distinguish gross/marketable/committed/unallocated quantities without applying losses twice. |
| A multi-step browser receipt reconciliation is mistaken for an atomic backend transaction | `LotsContext::reconcile` updates supply context then lot context; each persists separately | **Open P0 for operational use:** one server transaction plus receipt-scoped idempotency/version; repeated clicks, storage failure and multiple tabs must not decrement a reservation twice. Local guard/history does not establish atomicity. |
| “Saved” means durable/shared despite browser storage failure | Local services swallow localStorage errors; shared and trade writes use DB transactions | **Open:** propagate persistence outcome and display session-only/unsaved status; migrate operational writes to API acknowledgements. Current banner separates local from shared, but does not solve storage failure. |
| “Sent” or “paid” is mistaken for an external delivery/fund transfer | `PlanContext::sendInstructions` stores simulated messages; trade settlement records evidence and finance review | **Partial:** simulation labels and separate FPO receipt/member disbursal already exist; local banner reinforces the boundary. Actual messaging needs durable outbox/delivery receipts. A payment evidence record must never be presented as a Meraki-initiated transfer. |
| Different clocks and date meanings imply the same readiness | `planning/engine.ts::PLANNING_DATE`, live-source availability fields, trade server schedule | **Partial:** preserve fixed scenario date, decision/as-of, observation/publication time and server deadlines as separate fields. UI deadline previews are not authority; never train pre-sowing forecasts using future observed weather. |
| Synthetic POC yield becomes verified production capacity | `yieldPoc/model.ts`, `model_validation/`, `reports/model_validation.json` | **Already isolated:** POC has no operational publication path and production flag is false; real report still has zero eligible outcomes. Carry source/evidence kind through any future adapter; never treat dummy predictions as reviewed stock. |
| Translation changes identifiers/units or sends future private records to third parties | `i18n/AutoTranslator.tsx`, `i18n/autoTranslate.ts` | **Open before real data:** translate reviewed labels instead of identifiers, raw measurements, workflow enums or consent text; mark sensitive/API-data subtrees non-translatable and review third-party disclosure before connecting private records. Current fixtures do not establish permission for future private data. |
| “Reset all demo data” leaves orphaned local lots/lab/drafts or is read as a server reset | `PlanContext::resetDemoData` clears planning keys, not all newer stores or server state | **Open bounded cleanup:** define browser reset scope and clear related local records together after user action; preserve server ledger/audit and state that it is unaffected. Do not use reset to cancel a contract. |
| Fee-first execution plan contradicts subscription-first paid product | `EXECUTION_PLAN.md` section 14 versus supplied addendum | **Open P1 alignment:** adopt agreed subscription-first positioning, sponsored FPO entitlement and optional disclosed market fees. No billing gateway is needed for a labelled entitlement demo. Existing fees on signed transaction terms must not be silently rewritten by copy changes. |

## Smallest integration PR sequence

1. **Relationship/scoped entitlement + shared requirements.** One exporter and two FPOs; FPO approves scopes. Add minimal labelled subscription state, never authorisation by payment alone. Exporter B's direct-ID access to A's demand must fail. Include amendment/withdrawal/duplicate-demand history.
2. **Canonical FPO source and explicit projection publisher.** Stable organisation/plot-cycle/crop-variety-grade/week identity and immutable version; export only approved fields. Use exact grams and evidence kind, maintain low/base/high and availability timestamps. Partner-specific coverage queries update after one FPO revision; raw plot/soil/customer data remains private.
3. **Private allocation on the common source ledger.** Request/approve/decline/counteroffer with expected versions, expiry and idempotency. No marketplace listing required. Source-budget check and actual reservation/commitment must share a transaction; test repeated requests and simultaneous last-kg requests across capacity slices and revisions.
4. **Opt-in residual marketplace and withdrawal.** Explicit tranche/visibility grants; same budget as private allocations. Listing removal stops new offers, not signed obligations. Exporter C sees only published fields, not partner dashboards or competitors' private terms.
5. **Part 3 bridge using existing engines.** One verified principal/permission model, trusted QC lot linkage and canonical requirement/source/contract IDs. Award and shared reservation in one DB transaction, or an explicitly specified durable recovery protocol. Independent HTTP calls are insufficient. Both parties read the same lifecycle after refresh.
6. **Atomic fulfilment/reconciliation and notifications.** Receipt-scoped idempotency, append-only claims/weights, scoped document storage and separate finance evidence. Implement outbox states without implying funds moved; add restart/retry/restore and translated-data privacy acceptance.
7. **Positioning/measurement pass.** Subscription-first/sponsored FPO/optional marketplace in execution plan and UI; no production billing gateway required. Measure accepted-on-time kg, actual member net receipts/payment delay, costs and coordinator time without inventing uplift.

## Required end-to-end acceptance

- Exporter A has active approved relationships with FPO Alpha/Beta; subscription state alone grants no data access.
- A shared dated requirement drives a partner-approved plan/projection; updating one source updates A's coverage after refresh and does not leak to unrelated B.
- A 10,000 kg source can commit 4,000 kg privately to A and 2,000 kg to B without a market listing. Remaining source budget is 4,000 kg.
- An explicitly opted-in 1,000 kg market award leaves **3,000 kg** everywhere; simultaneous private/market requests and duplicate capacity/source attempts cannot recreate the pool.
- Relationship revocation stops future access/new bookings but retains signed obligations for explicit review/amendment/dispute.
- Lot/QC/dispatch/receipt/claims/settlement all reference that source and are visible to the appropriate parties after reload; no opaque QC reference or local-only checkbox releases operational stock.
- A database/API failure cannot show a successful local-only commitment or leave an orphaned reservation; retry of the same intent does not duplicate quantities.
- Simulated messages, synthetic yield, unverified payments and missing evidence remain visibly distinct.

This acceptance scenario is **not complete today**. Source guard regressions and individual module tests do not substitute for it.
